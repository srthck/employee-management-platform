# Audit chain: the transactional head (Phase 2)

Status: **implemented and tested; production activation requires the cutover in section 7.** The audit chain remains **tamper-evident, not tamper-proof**. Production statutory-wage calculation stays NO-GO; destructive snapshot recovery (`--apply`) stays disabled.

Companion documents: `CLAIMS-LEDGER.md` (what is established and how), `MODEL-RESULTS.md` (the Phase 1 models this implements), `../AUDIT-CHAIN-AND-SNAPSHOT-RECOVERY.md` (earlier design and its corrections).

## 1. What changed and why

Before: a writer read the highest record, computed `sequence+1` and `previousHash`, and inserted. Linearity depended on two unique indexes, and on a per-process cache that decided whether the indexes were still there. The independent review reproduced a committed fork, reported as success, whenever both indexes were absent or ineffective (finding F-01).

Now: one authoritative **head document**. Every append, inside the same transaction as the record, advances it by a conditional update. Two transactions cannot both advance the same head, so a writer that follows the protocol cannot fork the chain **whatever the state of the indexes**. The indexes stay as defence in depth, and a collection validator blocks writers that do not know the protocol.

What this does **not** do (stated, not hidden): it does not constrain a writer that bypasses the protocol and the validator (a raw client that fakes the `headVersion` field); it does not detect removal of the newest records (tail truncation); it does not by itself make business changes and their audit events atomic at the seven audit-only call sites where a business change has already committed (Phase 3); it does not give logical-operation idempotency (Phase 3).

## 2. The head document

Collection `auditchainheads`, one document, `_id: "global"` (the existing chain is global; its scope is unchanged).

| Field | Meaning |
|---|---|
| `sequence` | sequence number of the last committed record (`0` for an empty chain) |
| `hash` | hash of that record (`GENESIS` for an empty chain) |
| `version` | monotonic counter, `1` at creation, `+1` for every record |
| `scope`, `formatVersion` | `"global"`, `1` |
| `baseline` | where trust starts: `{sequence, hash, source, at, operator, planDigest, commit}`; `source` is `initialized-from-verified-history` (the operator procedure) or `auto-bootstrap-empty` (development/test, an empty chain only) |

Every record written under the protocol carries `headVersion`, the head `version` produced by the transition that appended it. `headVersion` is **not** part of the hash payload.

## 3. The append protocol (derived from the Phase 1 model `head-cas`; differences in section 8)

Inside one MongoDB transaction:

1. read the head (inside the transaction, so a second event in the same transaction sees the first event's advance);
2. build the record with the **existing** canonical hash: `sequenceNumber = head.sequence + 1`, `previousHash = head.hash`, `headVersion = head.version + 1`;
3. `updateOne({_id:"global", sequence: n, hash: h, version: v}, {$set:{sequence: n+1, hash: h'}, $inc:{version: 1}})`, requiring exactly one matching and modified document;
4. insert the record in the same session;
5. commit with the caller's business writes.

A lost race is a `WriteConflict` (or a non-match, which a snapshot transaction cannot normally produce): the transaction aborts and `runInTransaction` re-runs the whole unit of work from a fresh head. If the insert fails, the head advance rolls back with it. If the unique indexes refuse the insert although the head said the position was free, a writer outside the protocol has written to the chain: the append fails with `AUDIT_CHAIN_HEAD_INCONSISTENT` (503, not retryable; retrying cannot help) and nothing is written.

**Bounded failure.** `runInTransaction` re-runs the whole unit of work for at most 40 attempts or 15 s, whichever ends first. When that budget is spent on head conflicts the outcome is the explicit, retryable `503 AUDIT_CHAIN_CONTENTION` and nothing is written; callers can pass a smaller budget (`logStandalone(params, { maxAttempts, maxWaitMs })`, tested). With several application instances, or behind a long transaction in another process, an audited request can therefore be refused after about 15 s. This mechanism is unchanged by Phase 2 (the recovery document's superseded-design banner covers only the index guard and its cache).

**Multi-event transactions:** each event does steps 1-4 in order, so event *k+1* extends event *k* (verified by integration tests: consecutive sequences, linked hashes, `headVersion` 2, 3, 4). The head advances by one per record, as the model requires.

**Creating the very first head (relaxed mode only; strict mode never does).** Two transactions that both read "no head" on an empty chain both try to insert it. Observed on MongoDB 8.0.12 (single-node replica set), recorded by the tests as diagnostics rather than assumed: the server **accepts the overtaken transaction's insert when it is issued** and refuses the transaction later. With the unique indexes present the refusal is a `WriteConflict` at the record insert; with **every** unique index absent it is a `WriteConflict` at the commit (the head's `_id` is then the only arbiter). Either way the loser is re-run from the winner's head and the chain stays linear. A duplicate-key reply (code 11000) at the head insert is mapped to the same retryable conflict; on this server it is only seen in the no-transaction development fallback, where the loser previously gave up instead of retrying (found by mutation testing, fixed in this phase).

**Hash format unchanged.** `hashPayload`, `normalize`, `canonicalize`, `calculateAuditHash`, `verifyAuditChain` and `GENESIS` are byte-identical to the previous commit (checked by text comparison), and a pinned digest for a literal record is computed by the code of commits `2dfddaf`, `04c872b` and this one, and by an independent re-statement of the rules, with the same result. One historical property is preserved on purpose and must never be "fixed" without a migration: the original normalization renders **every JavaScript number as a decimal string** before hashing (`mongoose.isValidObjectId(number)` is true), so `sequenceNumber: 7` is hashed as `"7"`.

## 4. Sessions: no silent independent commit

| Call | Behaviour |
|---|---|
| `auditService.log(params, session)` | requires a caller-owned session **with an active transaction**; otherwise `AUDIT_SESSION_REQUIRED` (500) and nothing is written. Ended, committed, aborted or never-started sessions are refused. |
| `auditService.logStandalone(params)` | an audit-only event with no business mutation: opens and owns its transaction. Refused with `AUDIT_NESTED_TRANSACTION` from inside a `runInTransaction` callback (it would be a second, independent transaction that commits or blocks separately). |
| `auditService.log(params)` (no session) | refused (above), except in the **development fallback**: transaction policy honoured (loopback database, `NODE_ENV` development/test, explicit opt-out) **and** the server has no real transactions. There the head advance and the insert are two writes (not atomic); a failed insert reverts the head best effort. A caller that loses a race (the conditional update, or the creation of the first head) takes another turn, up to a fixed attempt limit. |

`auditService.log(params, session)` is also refused (`AUDIT_NESTED_TRANSACTION`) when the session belongs to a transaction that was **started from inside another transaction's callback**: that inner transaction would commit or block independently of its parent and contend with it on the single head (stall until the retry budget is spent, or its effects committed twice when the parent re-runs). A nested transaction that writes no audit event is still allowed.

A census (six tripwires in `test_audit_chain_head.js`, group E) scans the production sources. It is a **tripwire, not a proof**: regex based (a `/*` inside a string literal can hide code from it) and blind to code loaded from outside these directories. It pins (1) the exact inventory of files that touch the audit machinery, (2) that `auditService` is reached only as `auditService.<reviewed member>` (no alias, destructuring, optional chaining, bracket access, named or dynamic import), (3) that every `auditService.log(` call passes the identifier `session` and the per-file call counts (28 `log`, 10 `logStandalone`), (4) that only eight reviewed files name the audit models or collections and that the two trusted writers keep exactly their reviewed number of write-capable operations, (5) that the only code opening collections by a computed name and writing to them is `scripts/copy-database.mjs`, (6) that `logStandalone` is never lexically inside a `runInTransaction` callback. A new site fails a test until a human updates the table. The real enforcement is at run time.

**API consequence:** `log()` returns the persisted record as before. Because a transaction can be re-run, callers must not use a returned sequence number to make external decisions inside the callback; no production caller uses the return value.

## 5. Defence in depth: exact database shape

Judged by `auditChainSpec.js` against the live database (name-independent; key, order, uniqueness, partial filter, sparse, collation, TTL, hidden and an unfinished-build marker are all compared):

| Index | Key | Options |
|---|---|---|
| sequence | `{sequenceNumber: 1}` | unique |
| predecessor | `{previousHash: 1}` | unique, partial `{previousHash: {$type: "string"}}` |
| head transition | `{headVersion: 1}` | unique, partial `{headVersion: {$type: "number"}}` |
| validator | collection option | `$jsonSchema` requiring a numeric `headVersion >= 1`; `validationLevel: moderate`, `validationAction: error` |

* The **validator** is what blocks *unaware* writers: an old binary or script never sets `headVersion`, so the database refuses its insert (code 121). It is not a security boundary: a writer that fakes the field passes validation (tested and documented). `moderate` leaves updates of pre-existing records unvalidated.
* **Index creation and repair are no longer in the request path.** The earlier "guard" that rebuilt indexes inside an append (and could stall a request, or repeat a failing build on every request) is gone. The head and the validator are created only by the explicit initialization (section 7); the state is reported by `/api/ready`, `--status`, and startup logs. **What is NOT controlled:** the application process connects with Mongoose's default `autoIndex`, so every start builds the schema-declared indexes of every model, including the three unique chain indexes (additive and idempotent, but not a reviewed step). Starting a new binary before the cutover therefore may build those indexes in the background (readiness reports `INDEX_BUILD_RUNNING` meanwhile). This was left on deliberately: turning it off for the audit models would also stop the non-chain query indexes on a fresh installation.
* **Unfinished builds** are observable only through `$currentOp` on the admin database. Probe artefact `probe_listindexes_during_build_result.txt`: while `$currentOp` showed a build, `listIndexes` already listed the unfinished index in 716 of 718 samples and carried no marker, so an unfinished unique index is indistinguishable from a finished one (the evaluator's `buildUUID`/`building` check is therefore never triggered on this server version; it stays for servers that expose such a marker). The `$currentOp` check is best effort: when the database user lacks that privilege the status says `INDEX_BUILD_UNOBSERVABLE` (a **warning** in readiness, never "clean"), and the cutover tool **refuses** unless the operator acknowledges it with `--accept-unobservable-index-builds`. During a real build a status read that needs the collection lock can itself fail with a lock timeout (5 ms inside a transaction): readiness then answers not ready (fail closed). The test asserts the status is never healthy while a build runs.
* **Strictness trade-off of the specification.** The evaluator compares options literally, so some effective indexes are judged `INCOMPATIBLE` (a false alarm in the safe direction, a 503 in strict mode): a **hidden** unique index (it still enforces uniqueness; rejected deliberately because it can be dropped unnoticed from query plans and its state is easy to misread), a partial filter spelled differently but equivalent (`{$type: 2}` for `"string"`), or a default collation inherited from the collection. Remedy: drop the look-alike and re-run the tool, which creates the exact index (the tool never replaces an index by itself).
* **Mode policy (`src/config/auditChainPolicy.js`, an allow-list tested exhaustively and through the real config module in child processes).** Relaxed needs `NODE_ENV` to be exactly `development` or `test` **and** `AUDIT_CHAIN_STRICT` unset or `false`/`0`/`no`. Production, an unset/unrecognized/misspelled `NODE_ENV`, `AUDIT_CHAIN_STRICT=true|1|yes`, and any flag value the policy does not understand are **strict**. An unknown mode value at the code level is an error, never silently relaxed.
* Strict mode: a missing index, missing validator, missing or inconsistent head, or a running index build is an **error** and makes readiness fail; no code path ever creates a head. Relaxed mode: missing indexes/validator are warnings, and an **empty** chain creates its own genesis head, but only while every host this process is connected to is a **loopback** address (the environment label alone is not trusted: on a shared or remote database the first append is refused with `AUDIT_CHAIN_NOT_INITIALIZED` and the status calls the missing head an error). A head over a *non-empty* chain is never invented.
* **Readiness (`/api/ready`) fails closed and is cheap:** concurrent probes share one status computation, the computation is bounded by a 3 s timeout (`STATUS_TIMEOUT`), the answer is cached for 5 s, and the unauthenticated response carries only fixed codes (`severity:CODE`), never driver error text, host names or namespaces. It also reports the transaction lane (enabled, busy, queued, how long the holder has held it; no labels) without letting it decide readiness.

## 7. Initialization and cutover

`scripts/audit-chain-head.mjs` (dry run by default; strict argument parsing; connection with `autoCreate`/`autoIndex` off; the dry run and `--status` create no collection and no index).

1. **Drain every writer first**: HTTP instances, background jobs (stuck-run monitor, compensation activation), scheduled tasks, maintenance scripts. The tool cannot do this for you. All it checks is that the newest audit record is older than `--quiet-seconds` (default 60); that says nothing about connected but idle writers, and it compares the application's clock with the operator's machine. What it does do is block writers that do not know the protocol once it sets the validator (step 5).
2. If there are records without chain fields, run the explicit legacy migration **first** (`scripts/audit-chain-legacy-backfill.mjs`); once a head exists the migration refuses.
3. `node scripts/audit-chain-head.mjs` (dry run) — verifies the visible chain (fork, gap, bad link, edited record, a record it cannot read such as an unparseable `createdAt`, which is a `CHAIN_RECORD_MALFORMED` finding, not a crash), records without chain fields, protocol records without a head, incompatible indexes or validator, a running index build, an **unobservable** index build (the database user cannot run `$currentOp`: refused unless acknowledged, see step 5) and **recent writes**. It prints the **target** it inspected (database, hosts, replica set), the index build state, the exact actions and a **plan digest** that covers the target, the data, the actions and the acknowledgement. It refuses on any finding.
4. `node scripts/audit-chain-head.mjs --status` — read-only, judged as production would. **Before step 5 it is expected to report NOT OK and exit 1** (no head, no validator yet); an automated runbook under `set -e` must run it after step 5, or tolerate that exit status.
5. `node scripts/audit-chain-head.mjs --apply --plan-digest <digest> --confirm-database <name> --operator <you> [--commit <id>] [--report <new file>] [--json] [--accept-unobservable-index-builds]` — re-plans, requires the same digest (so a plan reviewed on one cluster cannot be applied to a restored copy that merely has the same database name), creates missing indexes, **sets the collection validator** (from this moment the database refuses new records from writers that do not know the protocol), then in one transaction re-reads the tail, requires it to equal the planned tail and record count, and inserts the single head. `--report` writes the evidence of this irreversible step to a NEW file (never overwritten); `--json` prints the same record. `--accept-unobservable-index-builds` is **your** statement that no index build is running on the audit collection; it is part of the digest. `--quiet-seconds 0` switches the recent-writer guard off and prints a warning.
   * *Interleavings with old writers, observed on a real server (MongoDB 8.0.12) and pinned by tests.* A head-unaware writer whose transaction snapshot **predates** the validator is refused when it inserts afterwards (a `WriteConflict` about catalog changes). One that **already touched** the audit collection makes the cutover wait for its transaction (a liveness cost: the tool's index build and `collMod` queue behind it); the record it then commits is caught by the tail re-check (`CHAIN_CHANGED_DURING_CUTOVER`).
   * *Racing initializers:* exactly one head exists; the others report `HEAD_ALREADY_EXISTS`. Two concurrent builds of the same missing index can make one initializer fail early; just re-plan.
   * *After `CHAIN_CHANGED_DURING_CUTOVER`, or a crash after the first step,* the database is left **fail-closed** (validator set, no head; audited operations are refused). Re-running needs a **fresh dry run and a new digest** (the actions shrank), and the record that caused the abort is itself recent, so the re-plan is refused as `RECENT_WRITES` until `--quiet-seconds` has passed, or until you pass `--quiet-seconds 0` and accept the warning.
   * *If the acknowledgement of a successful apply is lost,* a re-run reports `HEAD_ALREADY_EXISTS` and exits 1 although the cutover succeeded: run `--status`.
6. Deploy the new binaries only now. Do not restart old binaries: the validator refuses their inserts, and they would also be missing the head protocol. (A new binary started earlier would build the schema indexes by itself at startup, section 5; it still could not create a head in strict mode.)
7. Roll-back constraint: after a cutover, returning to the previous binaries requires removing the validator **and** accepting that the head becomes stale (the previous writers do not advance it); a later re-initialization is refused while a head exists. Treat the cutover as one-way; a rollback procedure is Phase 7 work.

**Limitation recorded in every head:** without an external checkpoint nothing can prove that records after the visible tail were not removed *before* the cutover. The head records the verified visible tail as the starting trusted baseline. A test documents that truncation before initialization is not detectable. **After** the cutover, removing the newest records while leaving the head alone is detected by `verifyHead`/readiness (the head then points beyond the chain); an attacker who also rewrites the head, or who removes records before the cutover, is not detected.

## 8. Mapping to the Phase 1 model

The protocol is **derived from** the Phase 1 model `head-cas`; it is not identical to it, and the model's verdicts (scenarios A5/A6) are evidence only for what the model contains. Differences, stated:

1. The model has one record per transaction. The implementation lets several events extend each other inside one transaction (integration-tested: consecutive sequences, linked hashes, `headVersion` 2, 3, 4; no model scenario exists for it).
2. In the model an insert refused by a unique index makes the writer retry. In the implementation an insert refused AFTER a successful head advance means a writer outside the protocol wrote to that position, and is `AUDIT_CHAIN_HEAD_INCONSISTENT` (503, not retryable).
3. The model's commit is one atomic first-committer-wins step. The implementation relies on the server's write-conflict detection, and its conditional update matches `{sequence, hash, version}`, not only the version.
4. The model has no per-process lane, no validator and no cutover; those are implementation mechanisms with their own tests (and, for the lane, a measured cost, sections 9 and 10).

| Phase 1 invariant | Mechanism | Evidence (class) |
|---|---|---|
| `OneSuccessorPerPredecessor` | the conditional head update; defence in depth: unique `previousHash` | barriered multi-process races under every index state (all present, each absent, all absent, look-alike partial filters, incompatible options) never fork, with the injected index fault asserted at release and after the race (`DIRECTLY_TESTED`); a **positive control** shows the same harness DOES observe a fork when the pre-head algorithm runs without indexes (`DIRECTLY_TESTED`); model scenarios A5/A6 (`SIMULATED`). Before the review fix the race workers silently rebuilt the dropped indexes through Mongoose `autoIndex`; that earlier evidence is withdrawn |
| `HeadMatchesLastCommittedEntry` | head and record written in one transaction; `verifyHead()` checks sequence, hash and version in one snapshot (six named disagreements, each tested; a concurrent append between its two reads is tested); `/api/ready` | assertions after every race and rollback test (`DIRECTLY_TESTED`) |
| `NoCommittedCriticalMutationWithoutRequiredAudit` | **only for the transactional sites** (event in the business transaction). **Not closed** for the seven F-05 sites — Phase 3 | rollback tests at every step (injected exceptions are labelled `SIMULATED`; the abort of a callback, the lost-commit cases and a real SIGKILL are real); ledger keeps F-05 open |
| `NoDuplicateLogicalOperation` | **not addressed** (Phase 3, operation ids) | `SIMULATED`: an injected commit failure on a real replica set (the commit really applied, then an error is raised) leaves the work committed exactly once, and the error does not claim a rollback; a commit that never reached the server leaves nothing committed and the caller again gets the raw unknown-result error. Behaviour under a real lost reply, failover or a `failCommand` failpoint is `UNVERIFIED` |
| Rollout condition (model A9/A10) | the validator refuses writers without `headVersion`; cutover tail check | old-writer tests (insert refused with code 121; a record sneaked in before the validator aborts the cutover; the two real-server interleavings of section 7) (`DIRECTLY_TESTED`) |
| Index-spec distinction (the model treats "dropped" as the worst case) | an ineffective index enforces no more than an absent one, so the model's worst case covers it; additionally tested explicitly | look-alike and incompatible index scenarios (`DIRECTLY_TESTED`) |

The Phase 1 mutation note stands: cache expiry changed no model verdict, and the cache no longer exists.

## 9. Performance (gate declared before measuring)

**Process, stated plainly.** Criteria were written and hashed before any run (`ACCEPTANCE_CRITERIA.md`, sha256 `33c6176b006a0cc88b54087306f9771d07826538f821846c05b6d2c385113d29`; file times show the criteria and their hash precede the first measurement): five synthetic workload shapes (W1 audit-only appends, W2 business+audit transactions over 20 company ids, W3 a payroll-finalization shape with 5 writes and 3 events, W4 bursts, W5 all together), pool `maxPoolSize: 10`, median of 3, thresholds relative to the baseline's own medians. The criteria say that a failing criterion fails the gate and that a scaling proposal is a separate, reviewed design. **That is not what happened, and the pass below must be read accordingly:**

* The head protocol **as first built FAILED the gate** (8 criteria on its first measurement; the same code re-measured later failed 11, including the safety criterion S6 with connection-pool checkout failures). A "deferred append" variant failed 9. A bench-only mutex experiment (not product code) passed everything, and the **per-process transaction lane** (section 10) was then written and adopted. The lane is a design change made *after* the gate failed; the gate was re-run on the redesigned candidate and passed. It is a **post-redesign pass, not a pre-declared one**, and the lane has not been reviewed as a scaling design. **That decision is flagged for the owners**: accept the lane (with the costs in section 10), or reject it and treat the gate as failed.
* The refusal criterion P2 counts every refusal of any kind (the harness records `refused:<code>` for any error), so a lane-wait refusal (`TRANSACTION_LANE_BUSY`) would have counted. None occurred.

**Controlled comparison (harness v2, one session, the four configurations back to back on the same machine state, AC power, no standby in the window; per-file provenance hashes are in each result JSON).** Median of 3 runs. Baseline = commit `9534553`, unmodified. Control = the same tree with the candidate's lane added. Lane-off = the candidate with the lane disabled.

| W2 | 7.0 → 62.2 → 63.6 → 8.8 | 32.7% / 0% / 0% / 40.3% | 14431 → 1591 | 19.1 → 1 (20.9) |
| W3 | 17.9 → 32.1 → 41.3 → 21.0 | 0% / 0% / 0% / 0% | 3190 → 609 | 8.9 → 1 (9.4) |

What this shows, and what it does not:
* **The candidate meets every declared criterion; the control also meets them; the candidate with the lane off fails ten.** The gains over the baseline on W2, W4 and W5 are the **lane's**, not the head protocol's: the old design plus the lane gets nearly all of them. Relative to that control the head protocol itself is roughly cost-neutral (W1 66.4 → 65.8, W2 62.2 → 63.6, W3 32.1 → 41.3, W4 53.5 → 54.5, W5 72.5 → 62.2, i.e. −14% on the mixed load; with three runs per configuration a difference of this size cannot be separated from run-to-run variation, so the honest statement is "no measurable cost shown", not "no cost").
* **Without the lane the head protocol is not acceptable** under in-process concurrency (W1 0.45× throughput and 4.5% refused, W5 84% refused): every transaction of a process that overlaps another's head advance re-runs, and a transaction's snapshot is fixed at its first operation. The lane is therefore load-bearing for liveness, not an optimization.
* **The baseline itself violates the declared limits** on this host state: 32.7% / 32.9% refused on W2 / W5 (limit 1%) and 8.9–19.1 callback runs per commit on four workloads (limit 3.0). Retries under contention are not new with the head; the head adds about 4–9% more callback runs when the lane is off (20.9 vs 19.1, 9.4 vs 8.9, 16.3 vs 15.7).
* **W1 is host-state dependent.** The earlier session measured the candidate at 0.55× the baseline's throughput (per-run ratios 0.45–0.58, so one of its three runs was under the 0.5 limit; the pass rested on the median); this session measured 0.97×. An audit-only append is now a three-round-trip transaction instead of one insert, so its cost shows when the database is fast and hides when it is slow. The earlier results are kept in the evidence directory, labelled as another session.
* **Not measured, by choice:** a workload with a *long* transaction (a 5–30 s finalization) next to short audit-only events, which is where the lane's cost lies (section 10); and multi-process throughput against a baseline. The single informational multi-process run of the earlier session left no script behind and is not quoted here. All workloads are synthetic shapes, single process, short transactions; none is production traffic.

**What did not work, kept as evidence.** The first implementation (head advance immediately, no lane) failed the gate on 8 criteria (W5: 64% refused, 12% of baseline throughput; callbacks re-run up to 19× per commit). Measured cause: a MongoDB transaction's snapshot is fixed at its first operation, and a write to a document committed after that snapshot always conflicts, so every transaction whose lifetime overlaps another's head advance re-runs. A deferred append (head advance just before the commit) was tried and **did not help** (9 criteria failed) and was removed. A commit gate that makes transactions wait before committing was judged counter-productive on the reasoning that waiting only makes the snapshot staler; **no benchmark of the gate alone exists**, that is an inference. What works is serializing the audited transactions **of one process** (section 10).

## 10. The per-process transaction lane

`runInTransaction` makes transactions of one process take turns (FIFO), each holding the lane across all its attempts (including the back-off sleeps between them); a waiter that waits longer than `maxQueueWaitMs` (60 s) fails with a retryable `503 TRANSACTION_LANE_BUSY` and writes nothing. It is a **liveness mechanism only**: safety rests on the conditional head update, and the race tests switch the lane off to prove it. A transaction started from inside another's callback does not wait for it (no deadlock) and is marked *nested*; an audited append in a nested transaction is refused (section 4).

**Costs, stated plainly:**
* **Availability coupling.** Every `runInTransaction` of the process shares the one lane, **including the audit-only events of login, account lockout and logout-all** (they are `logStandalone` calls and the login waits for its audit event before the cookie is issued). A long transaction in the same process (for example a payroll finalization) therefore delays them, up to the 60 s queue bound, after which the login fails with a retryable 503. The *holding* side has no time bound of its own: MongoDB's 60 s transaction lifetime limit bounds database work, but a callback that awaits non-database I/O could hold the lane longer (none exists today). Exempting the auth events from the lane would let them conflict with long transactions instead (and a long transaction re-runs on any concurrent head advance), so it is a trade-off for the owners, not a defect with an obvious fix. **Not measured** (the long-transaction workload was not run).
* **One hung transaction blocks the whole process.** Seen accidentally while developing the tests: after a test left a transaction open, every later transaction of that process failed with `TRANSACTION_LANE_BUSY` for 60 s each. The lane's state is visible: `/api/ready` reports `enabled`, `busy`, `queued` and `heldMs` (no labels), and `transactionLaneStatus()` names the holder inside the process. It does not affect readiness.
* Throughput is bounded by roughly 1 / (transaction duration) per chain, whatever the number of processes: the global chain is a deliberate serialization point.
* **Across processes** a long transaction can still be starved: any other process's head advance during its lifetime makes it re-run. Not observed in these workloads; not ruled out for long finalizations under heavy multi-process load. **A scaling proposal (per-company chains, or an outbox with a single sequencer) is a separate, reviewed design decision; none is made here.**
* **A crashed process stalls audited writes of every process.** A real `SIGKILL` of a process holding an uncommitted head advance (test D): nothing it did persists, but its transaction keeps the head write-locked until the server discards it; with `transactionLifetimeLimitSeconds` lowered to 3 s, audited writes resumed **about 4.1 s** after the kill (4074, 3971 and 4081 ms in three runs), meaning the server does not abort on disconnect and the stall is roughly the lifetime limit. With the server's default of 60 s the stall would be about a minute (extrapolated, not measured), during which audited requests are refused with the retryable `503 AUDIT_CHAIN_CONTENTION`.

## 11. Remaining gaps (not closed by this phase)

* F-05: seven audit-only call sites append after a business commit (a business change can exist without its event) — Phase 3. Three more audit-only sites have no business change (section 6).
* F-04: an ambiguous commit still surfaces as the driver's raw error; no `COMMIT_OUTCOME_UNKNOWN`, no operation ids / idempotency — Phase 3. The tests labelled SIMULATED (an injected commit failure on a real replica set; a commit that never reaches the server) show the work committed once, respectively not at all, and an error that claims neither. A `failCommand` failpoint, a real lost reply and failover are `UNVERIFIED`.
* F-09: tail truncation before the cutover, or together with a rewritten head, is undetectable without an external checkpoint — Phase 5. Removing the newest records after the cutover while leaving the head alone is detected (`verifyHead`, readiness).
* **The head check is not a chain walk.** `verifyHead` and readiness compare the head with the newest record. A fork buried in history, or a head-unaware writer that fakes `headVersion` and takes the next position while the unique indexes are ineffective, is **not** detected at append time (both pinned by tests, group F2); only `verifyAuditChain` finds it. `verifyAuditChain` itself still throws on a garbage `createdAt` (the cutover plan now turns that into a finding) — Phase 5.
* The protocol protects only writers that follow it. The validator blocks unaware writers and is not a security boundary (a writer that fakes `headVersion` passes it); anyone with `collMod`/drop rights can undo it.
* Failover / stepdown, a real standalone server, multi-host behaviour and the backup/restore procedure (section 6) are `UNVERIFIED`; the single-node replica set was the only topology.
* The relaxed (development/test) mode is a convenience; the production path is strict.
* **The unexplained 49 s zero-commit race, now with a candidate explanation.** In one execution of the head test file (lane off, three worker processes, "ALL unique indexes absent") no operation committed in 49 s. The whole run was about five times slower than normal (257 s against about 54 s; the group 168 s against 26 s; unrelated race tests 9–11 s against 1.2–1.6 s). No Modern Standby overlapped it (the last one ended six minutes earlier); power-source changes at 21:21 and 21:41 bracket it. The independent review found that **the race workers re-created every dropped index through Mongoose `autoIndex` while the race ran** (confirmed by probe: a default-options worker rebuilt all eleven secondary indexes within three seconds); many concurrent index builds committing under exclusive locks on a slowed host, exhausting the 15 s / 40-attempt budget, is the most plausible mechanism. It was never reproduced. The workers now connect with `autoIndex` off and every race asserts the injected index state at release and afterwards; the matrix has passed in every execution since (a count is in the ledger). **Treat as likely explained, not proven.**
* The earlier index-fault evidence ("never forks with every index absent") was **not valid** for the multi-process configurations because of that rebuild. It is re-established by the corrected matrix, a positive control (the pre-head algorithm forks under the same harness when the indexes are absent and cannot when they are present), and an in-process paused-writer test with every unique index dropped.
